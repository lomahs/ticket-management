Team Tracker: màn hình, API và xử lý

Bản đồ để catch up nhanh: user đi qua những màn hình nào, mỗi màn hình gọi API gì khi mở và khi bấm, và backend xử lý từng API ra sao (router → use case → domain → DB/Jira). Tất cả API nằm dưới /api/v1.

GET đọc POST PUT PATCH DELETE Jira đọc gọi JiraReader trực tiếp Jira ghi cần JiraWriter, phase 1 trả 403 full sync chạy lại sync toàn bộ

Một request chạy qua những lớp nào

Mọi màn hình đọc dữ liệu từ SQLite, không gọi Jira khi render. Jira chỉ được chạm khi sync, khi ghi (rồi refresh lại các issue vừa ghi), và ở vài API trong Settings.

Hai mode chạy

Profile demo (SPRING_PROFILES_ACTIVE=demo): DB mới, seed team mẫu, FakeJira vừa đọc vừa ghi, ngày cố định. Không có profile: JiraCloudReader, không có bean JiraWriter nên mọi API ghi Jira trả 403, có @Scheduled sync định kỳ.

Ai là "tôi"?

Phase 1 chưa có login. My Work và Sidebar lấy member từ localStorage pref me (mặc định binh) hoặc ?member=.

Cache sau khi ghi

Mọi mutation thành công gọi queryClient.invalidateQueries() không tham số, nên tất cả màn hình refetch. Mutation ghi Jira có mutationKey ['write', …] để SyncPill hiện "Writing…".

Lỗi

Request sai (Bean Validation, JSON hỏng, sai kiểu) 400 · Invalid 422 · NotFound 404 · Conflict 409 · CapabilityDisabled 403 · file quá 5 MB 413 · Jira lỗi 502. Body là problem detail (RFC 9457) kèm code và errors. Frontend unwrap() biến thành ApiError; mất mạng thành status 0.

TrackerContextLoader: pipeline chung của hầu hết API đọc

My Work, Anken, Matrix, Planning, Effort, Ticket và Q&A đều bắt đầu bằng TrackerContextLoader.load() (application/TrackerContextLoader.java). Nó load toàn bộ issue của các epic đang track rồi tính flag trong bộ nhớ, nên mỗi request là một lần tính lại từ đầu. Team Calendar và Settings không dùng nó.

flowchart LR
  A["settings.load()"] --> B["members.findAll()"]
  B --> C["calendar()<br/>leaves · holidays · extra days · ngày làm việc"]
  C --> D["anken.findAll()<br/>lọc theo epics đang track"]
  D --> E["issues.findByEpics(tracked)"]
  E --> F["Flags.buildFunctions(subtasks)<br/>gom theo (epic, function_id) thành 5 ô step"]
  F --> G["Flags.issueFlags() cho từng issue<br/>is_current · late · soon · over · tone · held_days · rounds"]
  G --> H["TrackerContext.card(issue) → TaskCard"]
5 step của một function

Create (BA) → BAL Review (BAL) → Fix comment BAL (BA) → JM Review (JM) → Fix comment JM (BA). Function id, tên và step được parse từ summary sub-task theo Name rule.

Status nội bộ

N Not yet started · W WIP · R Resolved · C Closed. Map từ status Jira theo tên (Status mapping) hoặc theo category new / indeterminate / done.

worker vs assignee

Flags.workerOf(): step review do assignee làm, step không phải review tính cho owner của function (assignee của Create). Planning và Timesheet xếp việc theo worker.

Sync với Jira

Có ba nguồn kích hoạt SyncService.run(), cùng một khoá running nên mỗi process chỉ chạy một sync tại một thời điểm. Mọi thứ được đọc từ Jira trước, rồi mới ghi vào DB trong một transaction ngắn, nên Jira chậm không giữ khoá ghi của SQLite. Lỗi được ghi vào sync_runs chứ không ném ra ngoài, nên POST /sync vẫn trả 200 với status: failed.

Các flow ghi chính

Ba flow ghi Jira đều theo mẫu preview trước (không ghi gì), rồi mới ghi thật và refresh. Ở jira mode phase 1, bước ghi trả 403 và UI disable nút qua useCapability('jiraWrite').
